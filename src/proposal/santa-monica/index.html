Executive Summary

The City of Santa Monica already uses Ranked Choices for commission and board appointments. This proposal outlines a path to expand that capability to city-wide community engagement and, potentially, municipal elections.

The work is structured in three phases:

Phase Scope Estimated Cost Timeline
1 Dedicated city platform $6,000 – $9,000 2–4 weeks
2 Resident voting system with blockchain audit $30,000 – $45,000 2–3 months
3 Municipal election readiness (future vision) — —
Total (Phases 1 & 2) $36,000 – $54,000 ~3–4 months

All software produced will be open source. The city pays for development time, not licenses. Santa Monica owns the result.

What Exists Today

Ranked Choices is a production web application with 5,000+ registered accounts and 350,000+ votes cast over the past decade. In 2026 alone: 11,000+ ballots and 1,800+ new accounts. Santa Monica has used it over a dozen times for commission appointments since 2025.

Current Capabilities

  • Ranked choice voting with instant-runoff and multi-seat (STV) algorithms
  • Secure ballots with unique voter codes (6-character alphanumeric)
  • QR code generation for voter code distribution
  • Auto-fill voter code from QR scan
  • Real-time animated results visualization
  • Borda count scoring as an alternative method
  • Drag-and-drop voting optimized for mobile (55% of traffic is mobile, 44% desktop)
  • Open-source codebase (PHP/MySQL backend, JavaScript frontend)

Organic Adoption — Zero Marketing, Real Usage

Ranked Choices has never spent a dollar on advertising. Every user found it because someone shared a ballot link — via text message, email, or a classroom assignment. In 2026, over 15,000 referral visits came from schools, workplaces, and government agencies.

68% of all traffic is direct links — the same share-and-vote model proposed for Santa Monica resident engagement. Someone sends a link, the recipient opens it and votes. The analytics prove this flow works at scale.

The top organic referral sources tell the story:

  • Google Classroom — teachers running mock elections and civic education exercises (avg. 4 minutes on site)
  • Microsoft Teams — organizations making workplace decisions (avg. 2 minutes)
  • Government Teams (.gov) — federal and state employees sharing ballots through official infrastructure
  • University platforms — Schoology, Blackboard, and college portals
  • AI assistants — ChatGPT actively recommends Ranked Choices to people searching for RCV tools

Every one of these referral sessions is organic — someone chose to share a specific ballot. No resource pages, no paid placements, no SEO campaigns. The platform grows because people use it and pass it along.

Resident Voting System

2–3 months 200–300 hours $30,000–$45,000

Verified Santa Monica residents participate in ranked-choice community decisions — participatory budgeting, planning input, advisory polls — using their own devices.

Resident Registry

  • City staff registers and verifies residents against city records
  • Each verified resident receives a unique voter code — reusable across all community ballots (single-blind: the city can verify participation, but results remain anonymous)
  • The resident's device is fingerprinted to their code so only that device can vote using that code, preventing fraud
  • Residant status management: (e.g. pending, verified, suspended)
  • Bulk import from existing resident databases
  • At the administration's discretion, specific ballots can use one-time codes instead — for double-blind engagement where not even the city knows how participants voted

Two Voting Channels

Mail-In Paper Ballots

Mail-in ballots are paper only — no electronic codes. The voter fills out a paper ranked-choice ballot and mails it back. Paper ballots are scanned and counted separately.

If a voter requested a mail-in ballot but shows up in person, the poll worker voids the mail-in ballot (surrendered or flagged) and issues a fresh electronic code. This prevents double-voting at the voter roll level — no code-to-person linkage required.

Single-Blind Voting Model
Who Sees Results Sees Who Voted Traces Code → Resident
Public Yes No No
Resident (voter) Yes No Only their own
City admin Yes Yes Yes

The city can verify every vote came from a verified resident. Residents cannot trace each other — preserving ballot secrecy. This mirrors the trust model of in-person public comment: the city knows who you are, your neighbors don't know how you voted.

Multi-Ballot Support

  • One voter code works across all city ballots the resident is assigned to
  • They vote on their device, at their convenience, within the voting window
  • "Election" wrapper for bundling multiple races or measures under one session
In-Person Double-Blind Voting
  1. Voter arrives at polling location, verifies identity with poll worker
  2. Poll worker marks voter roll and presses “Issue Code”
  3. System generates a unique 6-character code on the spot — no pre-generated lists to steal or leak. Only the hash of the code is stored in the database — even a database administrator cannot see or intercept usable codes
  4. Code prints on a card with QR code — the only place the plaintext code exists is the physical card. Voter takes it to a private area (severing the link between identity and code)
  5. Voter scans QR or types the 6-character code on their own device — QR is a convenience, the code is the fallback for older phones or accessibility needs
  6. Voter ranks choices and submits — code expires 15 minutes after issuance
  7. Voter keeps the card as a receipt (proves inclusion, not how they voted)

The 15-minute expiration prevents vote buying — a code cannot be sold and used later. If a voter doesn't submit in time, the code expires and their vote is forfeited. One chance, on site.

Double-Blind Code Lifecycle

Every voter code in the in-person double-blind voting model carries a public audit trail. All fields below are open data — anyone can inspect them. No exact timestamps, no sequential IDs, no demographic tags.

Code Metadata Fields
Field Set When By Whom Purpose
code_hash Issuance System (random) Unique 6-character voter identifier — stored as a hash only, never in plaintext. The printed card is the only place the usable code exists.
batch_id Issuance System Composite key (municipality-election-precinct-worker-sequence) — known from the QR code; batch seals after 30+ votes AND 30+ minutes
issued_by Issuance Poll worker ID Which worker generated this code (in-person only)
used Vote submission System Marked spent when a vote is cast — the torn admission ticket. A used code cannot be submitted again.
Built-In Fraud Detection

The public data tells a story. Normal patterns are distinguishable from suspicious ones — and anyone can check:

Pattern Normal Suspicious
Batch count per worker Workers have similar batch counts relative to shift length Worker #3 has 10 batches while others have 3
Unclaimed codes per worker ~5% unclaimed (normal) One worker has 40% unclaimed codes
Code expiration Voted within 15 minutes of issuance Code expired unused — possible handoff attempt

Every code is traceable to the worker who created it, grouped into public batches of 30+, and expires in 15 minutes. If a poll worker generates extra codes, the pattern is visible — abnormal batch counts, high unclaimed rates, and suspicious timing all surface in the public data, without ever revealing how any individual voted. All of this data is public and open source — anyone can audit it.

Blockchain-Anchored Audit Trail

Votes are collected in batches of 30+. When a batch seals, all its rankings are hashed together into a single cryptographic fingerprint. That fingerprint is published to a public blockchain — permanent and immutable. If anyone changed even one part of one vote after the fact, the hash would no longer match, and the tampering would be detectable by anyone.

How It Works
  1. Voter receives a QR code from their poll worker. The code contains a batch ID (e.g. SM-2026GE-P4-W12-003) — the voter knows their batch immediately. The code is stored in the database as a hash only — the printed card is the only place the usable code exists
  2. Voter submits their ballot. The system validates the code (hashes it, matches against the stored hash) and records the vote in the batch. Individual votes have no separate hash or identifier — they exist only as anonymous entries in the batch
  3. A batch seals after 30+ votes and 30+ minutes — then all rankings in the batch are published together, in random order. Batch open and close times are public; individual vote times are not recorded
  4. When a batch seals, a single batch hash is computed from all rankings in the batch. At election close, all batch hashes are sealed into a Merkle tree and the root is published to a public blockchain — permanent, immutable, verifiable by anyone
  5. Anyone can download a batch's published rankings, recompute the batch hash, and confirm it matches the Merkle tree. Changing any single ranking would produce a different hash and break the seal

Verification Through Recognition

After the election, a voter looks up their batch:

  1. They scan the batch's published rankings (30+ anonymous ballots) and recognize their own — “that's mine — Alice first, Bob second, Carol third — unchanged”
  2. They recompute the batch hash from the published rankings and confirm it matches the Merkle tree on the blockchain — the batch is intact, no tampering

The voter knows their vote is there. But they cannot prove it. There is no individual vote hash, no receipt pointing to a specific ballot — only a batch of 30+ anonymous rankings. A vote buyer asks “prove you voted for Alice” — the voter can only point to a batch of 30+ votes, some for Alice and some not. Dead end.

What Anyone Can Verify & What No One Can Do

What Anyone Can Verify

  • “Was my vote counted?” — The voter recognizes their exact rankings in their batch's published list.
  • “Was my vote altered?” — Recompute the batch hash from the published rankings — it must match the Merkle tree on the blockchain. Any change breaks the seal.
  • “Were any votes tampered with?” — Changing a single ranking in any batch changes its hash, which changes the Merkle root and breaks the blockchain seal.
  • “Were fake votes added?” — The total number of votes across all batches must match the total number of issued codes (code hashes are counted, not plaintext).

What No One Can Do (By Design)

  • “Prove how someone voted” — No link exists between a hash and a specific vote within a batch. Not for the voter, not for the city, not for a court order.
  • “Buy a vote” — A buyer cannot verify the seller actually voted as promised. The receipt proves inclusion, not content.
  • “Identify a voter from public data” — No timestamps, no sequential IDs, no demographics. Only UUIDs, opaque hashes, and worker batches of 30+.

This is the balance that election security researchers have sought for decades: voters can personally verify their vote was counted and unchanged, while no one — including the voter — can cryptographically prove how any individual voted. Verification through recognition, not proof. Trust without receipts.

Cost of blockchain anchoring: less than one cent per election. The entire cryptographic audit trail for a city-wide vote is essentially free. The security value is permanent.

Accessibility (ADA / Section 508)

If the city chooses to prioritize accessibility, the platform can be built to WCAG 2.1 AA standards — fully usable by voters who are blind, low-vision, or have motor impairments.

  • Full screen reader support for the ranked-choice voting interface (VoiceOver on iOS, TalkBack on Android, NVDA/JAWS on desktop) — as a voter touches or navigates to a candidate, the name is read aloud; as they move a candidate, the new rank position is announced; on submission, the full ranking is read back for confirmation
  • Keyboard-only navigation for all voting functions — no mouse or touch required
  • High-contrast mode and configurable font sizes
  • Multi-language support (Spanish, Russian — Santa Monica's key demographics)
Accessible Voting Mode for Blind & Low-Vision Voters

Rather than retrofitting drag-and-drop for screen readers, the system could offer a dedicated accessible voting mode — a guided, conversational flow designed natively for how blind users already interact with their devices:

  1. Prompt on entry: “This ballot has accessibility features for screen readers. Would you like to activate accessible voting mode?”
  2. Read all candidates: “There are 12 candidates for City Council. They are: Caroline Torosis, Brett Shuster, Daniel Hall…”
  3. Select first choice: “Who is your first choice?” — voter navigates a simple list by swiping, double-taps to select
  4. Confirm and continue: “Caroline Torosis is your first choice. Who is your second choice?” — selected candidates are removed from the list
  5. Optional exit at any step: “Would you like to rank another candidate, or are you done?”
  6. Final review: “Your rankings are: 1. Caroline Torosis, 2. Daniel Hall, 3. Brett Shuster. Would you like to submit, or make changes?”

No spatial reasoning required. No dragging. Each step is a simple, familiar list selection with continuous verbal confirmation. A blind voter ranks candidates as confidently and independently as a sighted voter.

A personal note: I spent a full year using my phone exclusively through VoiceOver after my screen broke. I understand firsthand how blind users interact with touch interfaces — the tap-to-identify, swipe-to-navigate, double-tap-to-activate patterns. This accessible voting mode is designed around those exact interaction patterns.

Municipal Election Readiness

Future Vision

If California law evolves to allow locally certified digital voting systems, the platform built in Phases 1 and 2 would be the natural foundation for binding municipal RCV elections.

This phase requires a change in California law. Today, all voting systems used in binding public elections must be certified by the Secretary of State and run on air-gapped, offline hardware. No web-based system — open source or otherwise — currently qualifies. Phase 3 represents what becomes possible if the legislative landscape evolves, not a deliverable on a timeline.

Security, Compliance & Integration

Cryptographic Verifiability

For binding elections, the system will use established cryptographic techniques — proven in real elections in Norway, Switzerland, and US municipalities — that allow any voter to verify their vote was counted and any auditor to verify the complete tally, while making it mathematically impossible for anyone to prove how an individual voted. This is an active area of election security research with open-source implementations available.

Open-Source Commitment

The argument for open source in elections is simple: if you can't see how the sausage is made, you can't trust the sausage. Open source means there's nowhere to hide.

What This Is — and What It Isn't

What it is

  • A secure, accessible, open-source platform for ranked-choice community engagement and voting
  • Blockchain-anchored audit trail for tamper-evident vote records
  • A system where any voter can verify their own vote and any auditor can verify the complete results
  • Built and owned by the city, maintained by a developer who believes in election integrity over profit

What it is not

  • A certified election system — California requires Secretary of State certification and air-gapped hardware for binding elections, which no web-based platform meets today
  • A replacement for the city's existing election infrastructure

The honest path: Phases 1 and 2 are well-defined and achievable with high confidence. Phase 3 is a vision — it represents what becomes possible if California law evolves to permit new classes of voting systems. I'd rather be upfront about that boundary than overpromise.

Why This Can't Be Used for Official Elections

California law draws a sharp line between how votes are counted (the voting method) and what system counts them (the voting system). A city can adopt ranked choice voting as its method. But the system that casts and tabulates those ballots must meet state requirements that no internet-based tool can satisfy today — and even a closed local network wouldn't qualify, since the law prohibits transmitting vote data over any communication network, including localized Wi-Fi.

These are the specific laws. Anyone who uses Ranked Choices and wonders why it can't simply be adopted for city council elections deserves a straight answer.

Elections Code §19205 — No Internet, Period

No part of a voting system may be connected to the internet at any time. No part may transmit or receive data through any external communication network. No part may use wireless communication of any kind.

A web application is, by definition, a system that sends and receives data over the internet. This statute is an absolute ban with no exceptions for tabulation-only tools, supplemental systems, or open-source software.

Cal. Elec. Code §19205

Elections Code §362 — What Counts as a “Voting System”

A “voting system” is any electronic system and its software used for casting a ballot, tabulating votes, or both. The only exception is remote accessible vote-by-mail systems (an accessibility accommodation, not a general exemption).

An RCV web application that tabulates ranked ballots meets this definition. Once classified as a voting system, every requirement in Division 19 of the Elections Code applies — including the internet ban above.

Cal. Elec. Code §362

Elections Code §19202 — Secretary of State Certification Required

No voting system may be used in any California election unless it has been certified or conditionally approved by the Secretary of State. No jurisdiction may purchase or contract for an uncertified system.

Certification requires testing by an accredited laboratory, a complete security review, source code escrow, and an air-gapped architecture. An internet-dependent system cannot pass this process. No web-based voting application has ever been certified in California.

Cal. Elec. Code §19202

Elections Code §19103 — Source Code Escrow

An exact copy of the source code for all ballot tally software must be placed in an approved escrow facility before the system is used. This applies to every version and every modification.

A web application that is continuously updated and runs server-side cannot satisfy this requirement in the way the statute contemplates — fixed, version-controlled binaries placed in escrow before each election.

Cal. Elec. Code §19103

Charter City Authority — Method Yes, System No

Under the California Constitution (Article XI, §5), charter cities have broad authority over municipal affairs. This is why San Francisco, Oakland, and Berkeley have adopted ranked choice voting for their elections.

But adopting a voting method does not exempt a city from voting system requirements. San Francisco uses a certified Dominion system to run its RCV elections — not a web application. Santa Monica can choose to count votes by ranked choice, but the equipment that casts and counts those ballots must still be state-certified, air-gapped, and offline.

What this means in practice: Everything in Phases 1 and 2 — commission appointments, community surveys, participatory budgeting — is fully legal because those are not official public elections under state law. Phase 3 is what becomes possible if California's legislative framework evolves to accommodate new classes of voting systems. Until then, binding elections must use the County's certified infrastructure. Ranked Choices could verify and visualize results from that infrastructure, but it cannot replace it today.

That said: If Santa Monica demonstrates a successful, transparent, and auditable system through Phases 1 and 2, it could strengthen the case for a pilot program or formal exception from the Secretary of State — the kind of precedent that changes what's possible statewide.
